# 지상국 사용법

기체 안의 컴퓨터는 **자세 제어(자세 안정)만** 합니다.
발사, 스로틀, 모터 정지, 노즈 분리는 모두 지상국 명령입니다.
지상국 프로그램은 `tools/ground_station.py` 입니다.

기체에는 안전 인터록(I1–I10)이 남아 있습니다. 어떤 명령으로도 끌 수 없습니다.
근거: `docs/SPEC.md` §8.8(명령·인터록), §10.3(LoRa 프레임).

기체의 비행 컴퓨터는 ATmega128A 3개(v0.6.3)입니다. 지상국과 무선으로 말하는 것은 **COM**이고, 명령을 실행하고 인터록을 판단하는 것은 **FCU**, 센서와 자세 추정은 **NAV**입니다.
지상국 쪽에서 보면 달라진 것은 없습니다. 프레임, 명령, 화면은 그대로입니다.
칩 사이 연결: `firmware/atmega128_fc/src/core/ilink_proto.h`(FCU–COM), `nlink_proto.h`(NAV–FCU).

> 괄호 안 숫자는 2026-10-15 `params.json`(v0.6.3) 값입니다. 값이 바뀌면 프로그램은 자동으로 따라갑니다. 이 문서의 숫자만 낡습니다.

## 1. 장비

| 물건 | 설명 |
|---|---|
| 노트북 | Windows 10/11. Python 3.12. |
| 지상 LoRa 모듈 | 기체와 같은 종류. 아래 A 또는 B. |
| 안테나 | 모듈 주파수 대역용. **안테나 없이 송신하면 모듈이 망가집니다.** |
| USB 케이블 | 데이터 전송 가능한 것. |

**A. Ebyte E22 / E220 / E32 계열 (UART 투명 모드)**

* USB-UART 어댑터(CP2102, CH340 등)에 연결합니다. 로직 전압은 모듈에 맞게 3.3 V로 둡니다.
* 결선: 어댑터 TX → 모듈 RXD, 어댑터 RX ← 모듈 TXD, GND 공통, 모듈 VCC는 모듈 사양대로.
* M0, M1은 GND에 연결합니다 (일반 = 투명 모드).
* 두 모듈(지상, 기체)을 Ebyte 설정 프로그램으로 **똑같이** 맞춥니다.
  * 채널, 주소, 공중 속도(가정 2.4 kbps, `link.lora_uart_air_rate_bps`).
  * UART 9600 8N1 (`link.uart_baud`).
  * 투명 전송(고정 전송 끔), RSSI 바이트 덧붙이기 끔.
* 공중 속도를 바꾸면 지연이 달라집니다. `params.json`을 고치고 시뮬레이션을 다시 돌리십시오.

**B. SX1276 계열 (SPI) 모듈**

* Arduino Nano 브리지가 필요합니다: `firmware/ground_bridge/README.md` (배선, 빌드, 업로드).
* 900 MHz대 모듈(RFM95W, Ra-01H 등)을 씁니다. Ra-01/Ra-02는 433 MHz용이라 안 됩니다.
* 실행할 때 `--radio sx127x` 를 붙입니다.

**주파수:** 국내는 KC 인증 920 MHz 대역 모듈을 씁니다. 433 MHz 사용 가능 여부는 확인되지 않았습니다.
전파누리(rra.go.kr)에서 먼저 확인하십시오. 출력·채널 점유 규정도 확인하십시오 (이 문서에서는 확인하지 않았습니다).

## 2. 설치

프로젝트 폴더에서:

```
.venv\Scripts\python.exe -m pip install pyserial
```

* 실제 비행 모드는 pyserial만 있으면 됩니다.
* 연습 모드(`--sim`)는 numpy가 필요합니다 (프로젝트 venv에 이미 있음).
* 포트 확인: `.venv\Scripts\python.exe tools\ground_station.py --list-ports`
* 창 크기: 가로 80자, 세로 26줄 이상이면 상태 화면이 위에 고정됩니다. 작으면 한 줄씩 출력합니다.
  작은 창에서도 상태 화면을 쓰려면 `--ui` (줄 끝이 잘립니다). 늘 한 줄 출력을 원하면 `--plain`.

실행:

```
.venv\Scripts\python.exe tools\ground_station.py --port COM5                 (Ebyte 모듈)
.venv\Scripts\python.exe tools\ground_station.py --port COM7 --radio sx127x  (SX1276 브리지)
```

`--radio` 는 응답 대기 시간을 정합니다. 모듈 종류와 꼭 맞추십시오.

| 무선 | 왕복 지연(모델) | 응답 대기 | 최대 물음 속도 |
|---|---|---|---|
| `lora_uart` (Ebyte) | 0.437 s | 0.531 s | 2.29 Hz |
| `sx127x` (브리지) | 0.198 s | 0.292 s | 5.04 Hz |

* 왕복 = 올라가는 시간 + 기체 안 처리 14 ms + 내려오는 시간.
  기체 안 처리는 COM이 명령을 받은 때부터 텔레메트리를 무선 모듈에 넘길 때까지입니다. 3칩 공동 시뮬레이션에서 잰 최대값을 올린 값입니다. 지금 보고서(`cosim_report.json`, 2026-10-16)의 최대는 UART형 12.5 ms, SPI형 13.2 ms입니다(`sim/link_model.py` 주석에 두 실행의 값이 모두 적혀 있습니다).
* 응답 대기 = 올라가는 시간 + 68 ms + 내려오는 시간 + 여유 40 ms. 68 ms는 응답 대기를 계산할 때 쓰는 기체 안 처리 한도입니다(`FC_REPLY_ALLOWANCE_S`).
  COM 펌웨어는 이 한도에서 정한 80 ms(`COM_REPLY_WINDOW_MS`)가 지나면 그 명령에 답을 보내지 않습니다. 그래서 늦은 답이 다음 물음의 답으로 섞이지 않습니다.
* 두 무선 모두 초당 2번(`poll_hz` 2 Hz) 묻습니다. 답을 기다리는 동안에는 묻지 않으므로 Ebyte는 2.29 Hz보다 빨리 물을 수 없습니다.

(`sim/link_model.py` 계산값. 실제 모듈로 측정해 고쳐야 하는 가정값이 섞여 있습니다. 기체 안 처리 시간도 실기가 아니라 simavr 시뮬레이션 값입니다.)

## 3. 화면

| 줄 | 뜻 |
|---|---|
| `STATE` | 기체 상태: SAFE, ARMED, POWERED, UNPOWERED, RELEASED, ABORT. `age`는 마지막 텔레메트리 이후 시간. |
| `flags` | ARM_SWITCH(아밍 스위치 닫힘), SENSORS_OK, ALIGNED(패드 정렬 끝), LINK_OK, RELEASED(분리 서보 열림), CONTROL_ACTIVE(자세 제어 중), REJECTED(마지막 명령 거부), INTERLOCK(인터록이 작동한 적 있음). 꺼진 것은 `---`. |
| `h`, `v_z` | 고도(패드 기준), 수직 속도. `predicted apogee`는 어시스트가 쓰는 예상 정점. |
| `att` | roll, pitch, yaw, `tilt`(기울기), throttle, V_cell(셀당 전압), loop_max(FCU 제어 루프 최대 시간). |
| `link` | delay(평균 왕복 시간), loss(응답 없는 요청 비율, 최근 30초), CRC 오류, 버린 바이트. |
| `reason` | 마지막 인터록 또는 거부 이유. |
| `ack` | 마지막 명령, SEQ, 보낸 횟수, 결과(pending / accepted / rejected / superseded). |
| events | 최근 사건 7줄. |

* 명령은 응답(ack)이 올 때까지 **같은 SEQ로 반복** 전송됩니다. 기체는 한 번만 실행합니다.
* `reason` 칸은 인터록과 거부가 같이 씁니다. 거부가 인터록 이유를 덮을 수 있습니다.
  그래도 `INTERLOCK` 플래그는 남습니다. 화면에 `[an interlock has acted since boot]`가 보이면 인터록이 작동한 것입니다.

## 4. 명령

| 명령 | 하는 일 |
|---|---|
| `arm` | SAFE → ARMED. 조건: 아밍 스위치 닫힘, 센서 정상, 정렬 끝, 기울기 < 5°(`arm_tilt_max_deg`), V_cell ≥ 3.3 V(`min_cell_v`), 링크 살아 있음. |
| `disarm` | ARMED → SAFE. |
| `launch` | ARMED에서만. `yes`를 쳐야 보냅니다. 모터가 `throttle_ramp_s`(0.5 s) 동안 `climb_throttle`(1.0)까지 올라갑니다. 논스는 자동입니다. |
| `throttle <u>` | 묶어 둔 시험(테더) 전용. `--allow-throttle-cmd`로 시작해야 0보다 큰 값을 보냅니다. `climb_throttle`로 잘립니다. ARMED에서 시작하면 확인을 묻습니다. |
| `cut` | 모터 정지. 자세 제어는 `coast_control_hold_s`(0.5 s) 더 합니다. |
| `release` | 모터 정지, `release_after_cut_s`(0.2 s) 뒤 노즈 분리. |
| `kill` / **Ctrl+C** | 비상정지. 비행 중: ABORT(모터 즉시 정지, `abort_release_delay_s` 0.5 s 뒤 분리). 패드: SAFE. |
| `assist on` / `assist off` | 자동 정지·분리 켜기/끄기. |
| `target <m>` | 어시스트 목표 고도. 0 초과 150 m(`apogee_limit_m`) 이하. |
| `status`, `help` | 상태 한 줄, 도움말. |
| `quit` | 종료. 기체가 ARMED/POWERED/UNPOWERED이면 확인을 묻습니다. |

* `cut`, `release`, `kill`은 앞서 기다리던 명령을 취소하고 먼저 나갑니다.
* `arm`, `launch`, `throttle`은 텔레메트리가 2초(`link_loss_disarm_s`)보다 오래되면 거부합니다.
  끊긴 동안 친 명령이 나중에 갑자기 나가지 않게 하려는 것입니다.
* Ctrl+C를 2초 안에 두 번 누르면 KILL 응답을 받은 뒤(최대 1.5 s) 종료합니다.

## 5. 비행 순서

**0. 준비**

1. 기체 펌웨어의 무선 종류(`link.radio`)와 지상 모듈 종류가 같은지 확인합니다.
2. 아밍 플러그를 뺀 채 기체 전원을 켭니다. 기체는 SAFE로 시작합니다.
3. 지상국을 켭니다. 로그 파일 경로가 화면 맨 위에 나옵니다.

**1. 거리 시험**

1. `STATE SAFE`, `LINK OK`, flags의 SENSORS_OK가 보이는지 확인합니다.
2. 기체(또는 같은 모듈)를 발사 위치까지 옮깁니다. 지상국은 대피 위치에 둡니다.
3. `delay`와 `loss`를 1분 이상 지켜봅니다.
   * delay가 표의 왕복 지연과 비슷해야 합니다.
   * 시뮬레이션은 손실 5 %를 가정했습니다. 10 %를 넘으면 안테나·위치를 고친 뒤 비행하십시오 (권장값, 실측 근거 없음).
4. 지상국은 초당 2번 묻습니다(`poll_hz`). 응답이 한 번 끊기면 다음 물음이 응답 대기(0.531 s) 뒤에 나가므로 기체 쪽 공백이 약 1.03초가 됩니다(Ebyte 기준).
   세 번 연속 끊기면 공백이 약 2.1초가 되어 기체가 ARMED에서 SAFE로 돌아갑니다(I1p). 손실이 낮아야 하는 이유입니다.

**2. 아밍**

1. 아밍 플러그를 꽂습니다. flags에 ARM_SWITCH가 켜집니다.
2. ALIGNED, SENSORS_OK, tilt < 5°, V_cell을 확인합니다.
3. 사람을 물립니다. `arm` 을 칩니다.
4. `ack ARM ... accepted`, `STATE ARMED`를 확인합니다. 거부되면 `reason`에 이유가 나옵니다.
   단, 인터록이 한 번이라도 걸린 뒤에는 `reason`이 그 인터록을 계속 보여 줍니다(전원을 다시 켤 때까지).
   이때는 flags(ARM_SWITCH, SENSORS_OK, ALIGNED), tilt, V_cell을 보고 거부 이유를 판단합니다.
5. ARMED에서 오래 기다리지 마십시오. 링크가 2초 끊기면 SAFE로 돌아갑니다.

**3. 발사**

1. 하늘·주변을 확인하고 카운트다운합니다.
2. `launch` → `yes`.
3. `STATE POWERED`, throttle이 1.0으로 오르는지 봅니다.

**4. 어시스트가 하는 일 (기본 켜짐)**

* 자동 CUT: 예상 정점 P = h + v_z·t_link + 1.20·v_z²/(2g)에 반 텔레메트리 간격만큼의 증가분(dP/dt × T_tel/2)을 더한 값이
  목표(140 m, `target_altitude_m`)에 닿으면 CUT을 보냅니다. t_link는 측정한 왕복 지연, 1.20은 `coast_drag_factor`, T_tel은 1/`poll_hz`와 t_link 중 큰 값입니다.
  S2 시뮬레이션에서 P는 초당 약 21.6 m 오르므로 텔레메트리 한 번(0.5 s)에 약 11 m씩 오릅니다. 반 간격을 앞당겨 목표 근처에서 끊습니다.
* 자동 RELEASE: 받은 v_z를 서보가 실제로 열릴 시각까지 앞으로 예측해서 0(`apogee_detect_vz_mps`) 이하가 되면 RELEASE를 보냅니다.
  예측 시간은 t_link + 0.2 s(`release_after_cut_s`) + 텔레메트리 간격의 절반입니다(`assist_release_rule` = predictive). Ebyte에서 약 0.89 s입니다.
  CUT 뒤 6 s(`coast_timeout_s`)가 지나도 보냅니다.
* **응답이 안 올 때 (v0.6.3)**: 응답 대기 시간이 지나도 답이 없으면 그 순간에도 위 두 규칙을 봅니다.
  마지막 텔레메트리를 받은 뒤 지난 시간 a만큼 앞으로 늘려 판단합니다. CUT은 P + dP/dt·a, RELEASE는 v_z − g·a(그리고 CUT 뒤 경과 시간에 a를 더함)입니다.
  그래서 텔레메트리 하나를 잃어도 CUT·RELEASE가 한 간격 늦어지지 않습니다. dP/dt를 아직 재지 못했으면(POWERED 텔레메트리 2개 전) 늘리지 않습니다.
  이때 events와 로그 `note`의 근거는 `no reply:`로 시작합니다 (근거: `sim/ground_station_logic.py`).
* 어시스트가 보낸 명령은 events와 로그에 `assist`로 표시되고, 판단 근거(h, v_z, 예상 정점)가 함께 남습니다.
* 남는 경우: CUT 명령 프레임 자체를 잃으면 응답 대기(0.531 s) 뒤에 다시 보냅니다. 그사이 기체의 I4(150 m 제한)가 먼저 모터를 끌 수 있습니다.
  이때 어시스트의 CUT 결과는 `rejected`로 나오고 이유에 I4가 보입니다. 이미 모터가 꺼졌기 때문이고, 안전 동작입니다. 얼마나 자주 생기는지는 6절에 있습니다.

**5. 수동 개입**

* 기체가 기울거나 이상하면 바로 `kill` 또는 Ctrl+C.
* 너무 높이 갈 것 같으면 `cut`. 정점이 지났는데 분리가 안 됐으면 `release`.
* 어시스트를 끄고 직접 하려면 `assist off`. 그래도 기체의 I4, I6은 작동합니다.

**6. 링크가 끊기면 (기체가 스스로 함)**

| 인터록 | 조건 | 동작 |
|---|---|---|
| I1p | ARMED에서 지상 프레임 없음 2.0 s (`link_loss_disarm_s`) | SAFE |
| I1 | 비행 중 지상 프레임 없음 3.0 s (`link_loss_abort_s`) | ABORT → 0.5 s 뒤 분리 |
| I4 | 비행 중 h + 1.20·v_z²/(2g) ≥ 150 m (`apogee_limit_m`) | 모터 정지(CUT)만 |
| I6 | v_z ≤ −8 m/s (`fall_deploy_vz_mps`)가 0.3 s 이어지고 아직 분리 전 | 분리(RELEASE) |

* 지상국은 `NO TELEMETRY x.x s` 를 빨리 보여 줍니다.
* 끊긴 동안 친 `cut`, `release`, `kill`은 줄에 남아 있다가 링크가 돌아오면 나갑니다.
* 지상국 프로그램을 끄는 것도 링크 끊김입니다. 비행 중에는 끄지 마십시오.
* 기체의 COM 칩이 리셋되어도 기체 상태는 바뀌지 않고, 리셋 뒤 링크가 다시 이어집니다. 공동 시뮬레이션에서 공백은 0.78 s였습니다(I1의 3 s보다 짧음).
* 비행 중 NAV 칩이 멈추거나 리셋되면 FCU는 마지막 정상 항법 프레임 0.1 s 뒤 ABORT(I9)하고 0.5 s 뒤 분리합니다. 화면에는 ABORT와 I9 이유가 나옵니다.
  (근거: `firmware/atmega128_fc/host_test/build/cosim_report.json`의 COM 리셋, NAV 정지·리셋 고장 시험. 실기 아님.)

**7. 착지 후**

1. `STATE RELEASED`를 확인합니다. 모터는 전원을 껐다 켤 때까지 다시 돌지 않습니다.
2. 기체에 다가가기 전에 아밍 플러그를 뽑게 합니다. 배터리를 분리합니다.
3. `quit`. 로그 파일을 보관합니다.

## 6. 연습 모드

```
.venv\Scripts\python.exe tools\ground_station.py --sim
```

* 가상 기체: 실제 기체 감독 로직(`sim/onboard.py`) + 링크 모델(지연, 손실 5 %, 기체 안 처리 시간 포함) + 단순 수직 질점 운동.
  추력, 질량, 항력, 낙하산은 `params.json`과 CAD 질량 보고서에서 옵니다.
* 자세는 시뮬레이션하지 않습니다. 비행 예측은 `sim/run_scenarios.py`(6자유도)를 보십시오.
* 명령은 실제와 같습니다. 연습 전용 명령이 더 있습니다.
  * `sim link off` / `sim link on`: 무선 끊기/잇기. I1p, I1을 연습합니다.
  * `sim switch open` / `sim switch closed`: 아밍 스위치 열기(= KILL)/닫기.
* 옵션: `--radio sx127x`(브리지 지연으로 연습), `--loss 0.2`(손실), `--seed 3`, `--speed 2`(빨리), `--no-assist`.
* 자동 조작: `--script "3:arm,6:launch,60:quit"` (연습 모드 전용). `--fast` 를 더하면 기다리지 않고 바로 끝납니다.

권장 연습:

1. 정상 비행: `arm` → `launch` → 어시스트 CUT, RELEASE 확인.
2. 수동 비행: `--no-assist`. 120 m쯤에서 `cut`, 정점이 지나면 `release`.
3. 패드에서 링크 끊김: ARMED에서 `sim link off` → 2초 뒤 SAFE(I1p).
4. 비행 중 링크 끊김: 상승 중 `sim link off` → 3초 뒤 ABORT(I1), 분리.
5. 비상정지: 상승 중 Ctrl+C.

연습 모드 측정 결과 (2026-10-16, v0.6.3 기체 2.59 kg, 시드 1–100, 손실 5 %, `--fast --script "3:arm,6:launch,60:quit"`).
이 문서를 쓰면서 돌린 결과입니다. 프로젝트 안에 보고서 파일로 저장하지 않았습니다. 같은 명령으로 다시 돌려 확인할 수 있습니다.

| 무선 | 비행 | 인터록 없이 끝남 | I4가 먼저 모터를 끔 | 실제 정점 | 정점 → 분리 |
|---|---|---|---|---|---|
| `lora_uart` | 100 | 90 | 10 | 133.8–149.0 m | −0.35 – +1.10 s |
| `sx127x` | 100 | 94 | 6 | 138.9–149.0 m | −0.19 – +0.82 s |

* 200번 모두 RELEASED로 끝났고, 정점은 모두 150 m 아래입니다. 착지 수직 속도는 모두 5.5 m/s입니다.
* 정점 → 분리는 두 무선 모두 100번 중 99번이 ±0.75 s 안입니다. 음수는 정점 직전에 열렸다는 뜻입니다.
  가장 늦은 1번(두 무선 모두 시드 95)은 CUT을 2번, RELEASE를 3번 보냈습니다. 프레임을 잃어 다시 보낸 것입니다.
* I4가 먼저 모터를 끈 비행: `lora_uart` 시드 2, 25, 29, 37, 41, 45, 55, 83, 84, 85 / `sx127x` 시드 2, 29, 37, 45, 69, 84. 정점 148.2–149.0 m.
  * 손실 패턴은 시드로 정해지므로 같은 시드가 겹칩니다.
  * 1번(`lora_uart` 시드 83)을 빼고는 CUT을 2번 이상 보냈습니다. 첫 CUT 프레임을 잃고 재전송을 기다리는 사이 I4가 먼저 모터를 끈 것입니다.
  * 어시스트의 CUT 결과는 `rejected`로 나오고 이유에 I4가 보입니다. 모두 안전 동작이지만 화면에 INTERLOCK이 뜹니다.
* 응답이 안 올 때 판단하는 규칙(v0.6.3)이 없으면, 같은 100개 시드에서 I4가 먼저 끈 비행이 15번(`lora_uart`) / 19번(`sx127x`)이었습니다. 규칙이 있으면 10번 / 6번입니다 (`sim/ground_station_logic.py` 설명; 위 표의 10 / 6과 같음).
* 남은 경우는 CUT 프레임 자체를 잃은 것이라 지상국 규칙으로는 없앨 수 없습니다. 거리 시험에서 손실률을 낮추는 것이 중요합니다.

## 7. 로그

* 위치: `logs\ground_station\gs_날짜_시각.csv` (연습은 `gs_sim_...`). `--log 경로`로 바꿀 수 있습니다.
* 실제 링크는 항상 기록합니다. 한 줄마다 바로 저장하므로 프로그램이 죽어도 남습니다.
* UTF-8 CSV입니다. 엑셀에서 열 수 있습니다.

| kind | 내용 |
|---|---|
| `TLM` | 받은 텔레메트리 프레임 전부. 예전 것보다 늦게 온 프레임은 `note`=`old`. `rtt_s`, `t_link_s`, `pred_apogee_m` 포함. |
| `UP` | 보낸 프레임 전부(하트비트 포함). cmd, seq, arg, nonce. |
| `TMO` | 응답이 없던 요청. |
| `CMD` | 줄에 넣은 명령(operator / assist). 어시스트 판단 근거가 `note`에 (응답이 없을 때 판단한 것은 `no reply:`로 시작). |
| `ACK` | 명령 결과(accepted / rejected: 이유 / superseded)와 보낸 횟수. |
| `EVT` | 지상 로직의 사건 기록. |
| `MSG` | 지상국 메시지(거부, 모드 변경 등). |

* `hex` 칸에 원래 바이트가 있습니다. 다시 디코딩할 수 있습니다.
* 다시 보기: `.venv\Scripts\python.exe tools\ground_station.py --replay logs\ground_station\gs_....csv`
  (`--speed 4` 빨리, `--fast` 바로 요약). 다시 보기는 아무것도 송신하지 않습니다.
