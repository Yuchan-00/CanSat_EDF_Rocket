# 제어 변경 이력 — v0.7.0 → v0.7.1

CanSat EDF VTOL(수직 이착륙) 기체의 제어 기준이 v0.7.0에서 v0.7.1로 바뀐 내용을 정리한 문서입니다. 변경마다 무엇을, 왜 바꿨는지 적고, 이전과 이후의 식·규칙·숫자를 나란히 놓았습니다. 각 변경을 보여 줄 비교 영상의 이름과 만드는 방법도 함께 적었습니다.

- 작성: 2026-10-21 (변경 목록 정리 단계)
- 같은 내용의 구조화 파일: `history/v0.7.1_changes.json` (영상 제작 단계가 읽는 계획 파일)
- 기준 자료: v0.7.0 = `history/v0.7.0/` (코드 묶음 `code_snapshot.zip`, 매개변수 `params.json`, 6자유도 기록 `vtol_logs/`), v0.7.1 = 현재 `params.json`과 기준 코드(`sim/estimator.py`, `sim/state_machine.py`, `sim/vertical_ctrl.py`, `sim/onboard.py`, `sim/nlink_proto.py`, `sim/link_proto.py`, `sim/fc_timing.py`)

> **상태 — v0.7.1 최종 결과는 아직 없습니다.** v0.7.1 6자유도 시뮬레이션을 지금 다시 돌리고 있습니다. 이 문서에 나오는 v0.7.1 숫자는 둘 중 하나입니다.
> - **(v0.7.1 결과 대기)**: 최종 실행이 끝나면 채워 넣을 자리입니다.
> - **중간값**: 재실행 중인 중간 기록(`sim/out/vtol/`, 2026-10-21 01:53)이나, 이 문서를 쓰면서 확인용으로 돌린 사전 점검 결과입니다. 사전 점검은 중간 게인(`sim/out/vtol_gains.json`, 2026-10-21 00:30)으로 돌렸습니다. 최종 결과로 바꿔야 하며, 발표 자료에 확정 수치로 쓰면 안 됩니다.

## 1. 비교를 정직하게 하는 원칙

v0.7.1에서는 제어만 바뀐 것이 아닙니다. 시뮬레이션 모델(공기 저항, 바람, 센서)과 판정 기준도 함께 바뀌었습니다(→ [M01](#4-m01-제어-아님-시뮬레이션-모델판정-기준-변경)). 그래서 모든 비교 영상에 둘 중 어느 비교인지 표시합니다.

| 구분 | 뜻 | 영상 제목 표기 |
|---|---|---|
| **격리 비교** | 양쪽이 **같은 v0.7.1 시뮬레이션 모델**에서 돌고, **이 변경 하나만** 다릅니다. v0.7.1 코드에서 옛 동작을 다시 고르는 방식입니다(예: 옛 자세 추정기 선택). | "같은 조건, ○○만 바꿈" |

v0.7.1 코드에서 옛 동작을 다시 고르는 데는 비교용 실행 도구를 씁니다(→ [7장](#7-비교-영상-만드는-방법)). 이 도구로 v0.7.1 기준을 그대로 돌리면 `sim/out/vtol/V_nominal` 기록과 지표가 소수점 끝자리까지 같았습니다. 따라서 격리 비교의 "이후" 쪽은 실제 v0.7.1 실행과 같다고 보아도 됩니다.

## 3. 변경별 상세

### C01. VTOL 자세 추정기 — 자이로만 → 가속도 보정 + 비행 중 바이어스 학습

**무엇을** 바꿨나: NAV 칩의 자세 추정기를 `PadAlignGyroEstimator`에서 `GatedMahonyEstimator`로 바꿨습니다(`sim/estimator.py`). VTOL 빌드에만 적용하고, 탄도 비행 빌드는 비트 단위로 같습니다.

**이전**
- 패드에서 자이로 바이어스를 평균하고, 가속도로 수평을 맞춥니다(2초 평균).
- 비행 중에는 q ← q ⊗ exp((ω − b_pad)·dt)입니다. 자이로만 적분하고, 바이어스는 패드에서 잰 값에 고정됩니다.

**이후**
- 패드 정렬은 같습니다. LANDED → SAFE로 다시 패드 모드에 들어오면, 착지한 자리의 가속도로 수평을 다시 맞춥니다.
- 비행 중 계산
  - 가속도 저역통과: a_lpf ← a_lpf + α(a − a_lpf), 차단 주파수 2 Hz(매개변수 가정값). 중간 튜닝값은 1.0 Hz입니다.
  - 게이트: | |a_lpf| − g | < 0.08 g일 때만 가속도를 씁니다. 가속 중에는 v0.7.0과 똑같이 자이로만 씁니다.
  - 오차: e = (a_lpf/|a_lpf|) × û_up(몸체 좌표).
  - 바이어스 학습: b = b_pad + clamp(b − b_pad − kᵢ·e·dt, ±0.6 °/s).
  - 자세 적분: q ← q ⊗ exp((ω − b + kₚ·e)·dt).
  - 매개변수: kₚ 0.15 /s, kᵢ 0.005 /s² (가정값). 중간 튜닝 파일: kₚ 0.15, kᵢ 0.01.
  - 설계 규칙: 1/kₚ이 항력 시간상수 τ_d(호버에서 6.51 s)보다 길어야 합니다.
  - 방위각(yaw)은 보정하지 않습니다. 자력계가 없기 때문입니다.

**왜** — v0.7.0 6자유도 결과(`report_vtol-sim.json`, `history/v0.7.0/vtol_logs`)
- 가정한 MPU-6050 바이어스 변동(최대 0.5 °/s) 때문에 약 40초 호버 동안 자세 추정이 **7.6°** 틀어졌습니다. 기체는 틀린 수직을 붙잡고 날았고, 수평 이동을 재는 센서가 없어 그대로 흘러갔습니다.
- 정상 비행(V_nominal): 착지 수평 속도 **7.66 m/s**, 기울기 7.5°, 패드에서 **119.8 m**.
- 몬테카를로 20회: 모든 기준 통과 **0/20**. 자세 추정 오차는 중앙값 7.6°, 최대 36.6°. 착지 수평 속도는 중앙값 6.2 m/s, 최대 14.7 m/s. 수평 속도와의 순위상관은 바이어스 변동 크기와 0.54, 바람과 0.04였습니다.
- 이상적인 자세 기준(실제 자세 + 0.5° 잡음)을 가정하면 모든 기준을 통과했습니다(0.30 m/s, 0.3°, 5.5 m). 원인이 추정기라는 뜻입니다.

**확인 영상**

  - 소스: `sim/out/vtol/V_nominal_pad_gyro.npz`(옛 추정기) vs `sim/out/vtol/V_nominal.npz`
  - 그래프: 추정 오차, 실제 기울기와 추정 기울기, 위에서 본 비행 궤적, 3D 나란히 보기

### C02. 고도 필터 — 가속도계 z 바이어스 상태 추가

**무엇을** 바꿨나: VTOL NAV의 고도 필터를 `AltitudeFilter`에서 `VtolAltitudeFilter`로 바꿨습니다(`sim/state_machine.py`). 탄도 빌드는 그대로입니다.

**이전**
- 상태는 고도 h와 수직 속도 v입니다. 예측은 h += v·dt + a·dt²/2, v += a·dt입니다.
- 기압계 샘플마다 r = (h_b + v·L) − h를 구해 h += k₁·r·dt, v += k₂·r·dt로 보정합니다. k₁ = 2ζω, k₂ = ω²이고, ω = 2π·0.5 Hz, ζ = 0.7입니다.
- 바이어스 상태가 없습니다. 기압계가 죽으면 가정한 10 mg 잔류 바이어스가 그대로 적분됩니다.

**이후**
- 상태 b를 추가하고, 예측에 (a − b)를 씁니다. 보정마다 b = clamp(b − k₃·r·dt_b, ±1.0 m/s²)입니다.
- 극점 배치: (s² + 2ζωs + ω²)(s + p), p = 1/40 s. 여기서 k₁ = 2ζω + p, k₂ = ω² + 2ζωp, k₃ = ω²p가 나옵니다.
- 패드에서는 h = v = 0으로 둡니다. 처음 2초(N틱)는 a의 단순 평균으로 b를 구하고, 이후에는 1/N EMA로 이어 갑니다. 기체가 정지해 있으니 a가 곧 바이어스입니다.
- 기압계를 잃으면 학습한 b로 예측만 합니다.

**왜**
- v0.7.0 기압계 고장 연구(20개 시드, 8 m 호버 중 16초에 기압계 정지): **7회가 최고 146.7 m까지 상승**했고, 60초 절대 한계(V6) 비상정지로만 멈췄습니다(비상정지 모두 8회). 착지한 12회 중 1 m/s 이내는 1회뿐이었습니다(중앙값 1.22, 최대 1.43 m/s). 출처: `history/v0.7.0/vtol_logs/vtol_metrics.json`의 `studies.baro_fail_seeds`.
- 바이어스 극점 선택(스크래치 연구 `v071/pyref/alt_filter_study.py`): 20 / 40 / 80 s일 때 바이어스 추정 표준편차는 0.0067 / 0.0034 / 0.0018 m/s²였습니다. 이륙 시 1.5 m 계단 오차에 대한 과도값은 0.12 / 0.062 / 0.031 m/s²였습니다. 그래서 40 s를 골랐습니다.
- 패드 단순 평균을 쓰는 이유: 2초 EMA는 전원 후 2.5초 만에 이륙하면 바이어스를 약 70 %만 배웁니다. 남은 오차는 20초 추측항법 뒤 0.2~0.5 m/s 오차가 됩니다(`td_study2.py`).

**확인 영상**: `cmp_C02a_altfilter_bias_isolated_V_baro_fail_s70` — 격리 비교. 필터만 v0.7.0 방식으로 바꿔 넣었습니다(바이어스 극점 1e12 s, 한계 0 = 옛 필터와 수학적으로 같음).

| V_baro_fail 시드 70 | 바이어스 상태 없음 | 있음 (v0.7.1) |
|---|---|---|
| 착지 수직 속도 | −1.16 m/s *(중간값)* | −0.75 m/s *(중간값)* |
| 착지 확인 | support, 2.1 s *(중간값)* | floor, 6.5 s *(중간값)* |
| 최종값 | (v0.7.1 결과 대기) | (v0.7.1 결과 대기) |

### C03. 기압계 고장 착륙 법칙 — 고정 하강 속도 → 내려가는 기준 고도 (플레어 없음)

**이전** (v0.7.0 `vertical_ctrl.py`): 기압계 고장으로 착륙할 때의 규칙입니다.
- h_ref = h로 둡니다. 추측항법 고도를 그대로 따라갑니다.
- v_cmd는 h ≤ 1.0 m이면 −0.3 m/s, 아니면 −0.6 m/s로 고정입니다. 고도 루프는 쓰지 않습니다.
- 착지 후보: |v_z| ≤ 0.15 m/s 하나뿐입니다.

**이후**
- 정상 착륙과 같은 법칙을 추측항법 고도(바이어스를 뺀 가속도 적분)에 적용합니다.
- 기준 고도는 0.6 m/s로 땅까지 계속 내려갑니다. 플레어는 없습니다.
- v_cmd = dh_ref/dt + alt_kp·(h_ref − h)입니다.
- 착지 신호는 추측항법 고도가 h ≤ 플레어 고도일 때만 셉니다(C05).

**왜** — 스크래치 연구 `v071/pyref/td_study2.py` (1-D 모델 + VTOL NAV 필터, 5 m 호버에서 기압계 고장 100회씩)

### C05. 착지 감지기 v2 — 신호 3가지

**이전**
- 후보 조건: |v_z| ≤ 0.15 m/s (원시 NAV v_z) 이고, v_cmd ≤ −0.3 이고, (h ≤ 1.0 m 또는 v_cmd ≤ −1.0)일 것.
- 0.5 s(125틱) 연속이면 착지로 확인합니다.

**이후**: 착륙(LAND) 중 아래 세 신호 중 하나가 0.5 s 이어지면 착지로 확인합니다.
- **still (정지)**: |저역통과 1.0 s(v_z)| ≤ 0.15 이고, alt_kp·(h_ref − h) ≤ −2 × 0.3일 것. 기준 고도가 기체보다 0.48 m 아래로 내려갔는데 기체가 따라가지 않는다는 뜻입니다. h ≤ 플레어 고도일 때만 셉니다.
- **support (지면 반력)**: 저역통과 0.2 s(f_z − g·r) > 0.25 g. 여기서 r은 명령 추력을 0.15 s 지연 모델에 통과시킨 T/(m g)입니다. 팬이 아닌 무언가가 기체를 받치고 있다는 뜻입니다.
- **floor (하강 한계 고정)**: 제어기가 아래쪽 한계에 1.0 s 붙어 있을 것. u가 u_min이거나, 적분기가 −vz_i_max이고 v_cmd가 −vz_max_down인 경우입니다.

- FCU가 NAV 쿼터니언과 몸체 z 비력(specific force)을 제어기에 넘겨 줍니다.

**왜**

### C09. 기준 고도를 정수(마이크로미터)로 계산

**이전**: h_ref += 상승률 × dt를 부동소수점으로 더했습니다(C는 float32, 파이썬은 float64). 목표 도착 판정(d ≤ 한 걸음)이 반올림에 따라 갈렸습니다.

**이후**: 기준 고도를 int32 µm로 계산합니다. 한 걸음은 round(속도 × 10⁶ / 250)입니다(1 m/s → 4000 µm). 목표는 정수 dm × 10⁵입니다. 두 언어에서 모든 비교가 정확히 같습니다.

**왜**: C 펌웨어와 파이썬 기준 코드가 6자유도의 모든 상승에서 CLIMB/HOLD 전환이 1틱씩 어긋났습니다. v0.7.1 교차검증(스크래치, 최종 아님)에서 수직 제어기 685,000틱, FCU 스택 271,958틱의 불일치가 **0틱**이었습니다.

**확인 영상**: `cmp_C09a_integer_reference_table` — 비행 영상이 아닌 슬라이드 또는 5초 애니메이션입니다. 비행에 주는 영향은 4 ms 틱 하나 이하라 눈에 보이지 않습니다.
